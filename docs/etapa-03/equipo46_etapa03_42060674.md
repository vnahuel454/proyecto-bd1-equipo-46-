## 1. Aporte realizado

En esta etapa me tocó encargarme de las tablas `PROVEEDOR` y `SUMINISTRA`. Escribí tanto la creación de las tablas (DDL) como la carga de datos de prueba (DML) y después las integré en los archivos generales del proyecto (`sql/ddl/crear_bd.sql` y `sql/dml/datos_prueba.sql`).

Para `PROVEEDOR` definí la clave primaria con el CUIT y le agregué una restricción CHECK para que valide que tenga 11 números exactos y no permita letras, además de pedir que la razón social sea única. Para `SUMINISTRA`, como conecta los proveedores con los productos, armé una clave primaria compuesta con el CUIT y el ID del producto, y configuré las claves foráneas con borrado y actualización en cascada para que no queden registros sueltos si se borra o cambia algo.

En la parte de datos de prueba cargué 10 proveedores con datos reales de empresas de distintas provincias y 11 registros en `SUMINISTRA` asociando esos proveedores a los productos que ya habían cargado mis compañeros. Al final dejé las consultas `SELECT` para verificar que todo se guarde bien y limpié los comentarios innecesarios del código para que quede prolijo.

## 2. Decisiones en las que participé

Hablamos con el equipo sobre cómo convenía encarar la tabla `SUMINISTRA`. Decidimos usar una clave primaria compuesta entre `cuit` y `id_producto` en lugar de inventar un ID numérico autoincremental, porque así evitamos que se pueda cargar dos veces el mismo producto para un mismo proveedor.

También definimos usar `ON DELETE CASCADE` y `ON UPDATE CASCADE` en `SUMINISTRA`. Si un proveedor se da de baja o se actualiza su CUIT, queríamos que la base lo replique sola sin tirar error ni dejar filas colgadas. Para el CUIT acordamos meter la regla con un CHECK a nivel de base de datos para no depender solo de validaciones externas. Por último, coordiné con el grupo los IDs de los productos para que mis inserts de suministros apunten a productos que de verdad existan en la tabla `PRODUCTO`.

## 3. Problemas o dificultades identificadas

La mayor dificultad de esta etapa fue coordinar los cambios en Git y GitHub. Como todos estábamos trabajando sobre los mismos dos archivos (`crear_bd.sql` y `datos_prueba.sql`), cada vez que alguien subía su parte a `main` se me generaban conflictos de merge al intentar fusionar mi rama. 

El otro tema fue el orden de las tablas en el SQL. Como `SUMINISTRA` tiene claves foráneas que apuntan a `PROVEEDOR` y a `PRODUCTO`, si no se crean esas dos tablas antes, SQL Server tira error. Lo mismo al borrar tablas con `DROP`: hay que borrar primero las intermedias antes que las tablas maestras.

## 4. Soluciones o propuestas realizadas

Para solucionar los conflictos de Git, fui trayendo los cambios actualizados de `main` a mi rama con `git fetch` y `git merge origin/main`. Tuve que resolver conflictos dos veces: primero cuando mis compañeros subieron las tablas de personas, clientes y empleados, y después cuando agregaron las de productos y categorías. En ambas ocasiones me fijé de no tocar nada del código que ellos ya habían hecho y ubicar mis tablas abajo de `PRODUCTO` para que el script corra sin errores de dependencias.

También estuve ayudando con las revisiones en GitHub, aprobando los Pull Requests de mis compañeros (como el PR #37) para que podamos ir avanzando en orden sin pisarnos.
